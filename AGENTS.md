# AGENTS.md

Instructions for AI coding agents working on **Crewlink**. Read this first. Before changing a folder, read the short README inside it.

## What Crewlink is

Crewlink is a place where people who share an idea or goal find each other and start building together.

- First part being built: **Crewlink for GitHub**. An owner connects a GitHub repo, shares one join link, and decides who comes aboard.
- Later, the same core will support other groups: college clubs, city communities, event teams.
- Crewlink **only connects people**. It does not manage how a team performs afterwards, and it is **not a chat app**. After approval, people continue in GitHub, WhatsApp or Discord.

## Core flow (must keep working)

1. The **owner** signs in with GitHub and creates a project from a repo they administer (admin access is checked).
2. The owner chooses how people join:
   - **Private (default) — referral link**: the project stays out of Discover and Explore. The owner shares one reusable invite link and approves each person who joins through it. Each project has one unique code; usage is unlimited by default, with an optional usage limit or expiry date, and the owner can revoke or regenerate the link.
   - **Public — direct join**: the project appears in Discover and Explore. Anyone signed in with GitHub can request to join; the owner still approves or rejects each request.
   - **Public — screening first**: the project appears in Discover and Explore. People complete the owner's own test or interview link before approval.
3. The owner gets one **join link** and shares it.
4. An **applicant** opens the link, signs in with GitHub and requests to join. The owner sees their account age and public repo count.
5. The owner approves or rejects. Approving marks the applicant as a **Crewlink contributor**; it never adds them as a GitHub collaborator or grants write, maintain or admin access. Contributors fork the repository and open pull requests that the owner reviews and merges.

UI rules: lock icon = private repo, globe icon = public repo. Clicking a public project opens its code on GitHub.

## Tech Stack & Commands

Built with **Next.js (App Router)**, **TypeScript**, **Tailwind CSS**, and **Lucide Icons**.

```bash
npm test        # run all automated tests, all must pass
npm run dev     # start development server at http://localhost:3100
npm run build   # build production application
```

Settings come from `.env` (copy `.env.example`). GitHub App / OAuth setup steps are in the root README.

## How to work

- Rule of thumb: **change one small piece, run `npm test`, test by hand with two GitHub accounts, then commit.**
- Tests use a **fake GitHub**. Add or update a test for any behaviour you change.
- Follow the style of the code around you. If you change what a folder does, keep its README accurate.
- Commands you write into READMEs or instructions must work in both PowerShell and bash (no bash-only syntax such as `export` or `&&` chains).
- If something is not covered here or in a README, say so and ask. Do not invent requirements.
- Keep reports short: what changed, what you ran, what is still untested.

## Boundaries

**Always**
- Run `npm test` before saying a task is done.
- Keep GitHub calls inside `src/github/`.
- Enforce owner-only approve and reject on the server, not only in the UI.

**Ask first**
- Changing the core flow or the three join modes.
- Showing owners more applicant data than account age and public repo count.
- Changing the GitHub App's permissions.
- Anything about payments, premium tiers or featured listings (the business model is not validated).
- Deciding any of the open decisions below.

**Never**
- Commit, print or share `.env` or the GitHub App private key file.
- Call real GitHub from automated tests.
- Post anything for an owner without their approval.
- Add chat features or team-performance tracking.
- Say a GitHub change "works" before the two-account test passes.
- Build publishing adapters, OAuth/install flows, publishing UI or AI drafting outside an approved milestone. Milestones 1 (credentials, secrets, connections), 2 (Discord/Telegram publishing), 3 (Bluesky/Mastodon account publishing), 4 (X manual + automatic publishing), 5 (Reddit), 6 (LinkedIn member publishing), 7 (Slack publishing + WhatsApp manual sharing) and 8 (AI social media agent) are approved; do not start any further milestone without explicit approval.
- Send real Discord, Telegram, or Slack messages outside an approved live test; mock transport is the default.

**Publishing Milestone 2:** Crewlink-owned Discord and Telegram bots. Owners connect a channel only (never a bot token); membership and minimum posting permissions (Discord View Channel + Send Messages with overwrite precedence, Telegram admin + `can_post_messages`) are verified server-side before a connection becomes active. Publishing requires the project owner, an approved draft whose text and sha256 hash still match, and an active connection. `publications` records one attempt per draft and platform (`sending` → `published`/`failed`), store only a content hash, refuse duplicate/in-progress sends, and allow a manual retry after failure. Retries use a conditional claim so concurrent retries cannot double-send; changing the destination channel invalidates approvals; stale or unrecorded sends are reported as `uncertain` and are never resent automatically. Discord and Telegram have separate clients and no shared state; a missing bot token fails closed. `PUBLISHING_TRANSPORT=mock` is the default and makes no network calls; `live` uses Discord Bot API v10 and the Telegram Bot API without automatic retries. The `publications` Prisma model has **not** been pushed to the connected database.

**Publishing UI:** owner-only `/publishing` page for Discord, Telegram, X, Reddit, and LinkedIn. Owners connect, change, or disconnect a destination; generate, edit, save, and approve drafts; and publish with an explicit click. Each draft shows Needs approval, Ready, Publishing, Published, Failed, or Check the channel. Failed sends can be retried manually. Uncertain sends are never retryable in the UI or the API: the UI shows no action and the API still returns 409. The page is a client over the existing owner-enforced APIs and adds no posting logic.

**Publishing Milestone 3 (Bluesky + Mastodon):** creator-owned account connections and publishing adapters, isolated in `src/posting/adapters/`. Bluesky signs in with an app password through the AT Protocol, stores only the resulting access/refresh JWTs (encrypted by the M1 vault), and never stores the app password. Mastodon registers an OAuth app per instance, requests only `read:accounts write:statuses`, stores the access token encrypted, and records the normalized `instanceUrl`. OAuth state is stored only as a sha256 hash with a 10-minute expiry; the pending client secret is encrypted with the same vault. Instance URLs must be public HTTPS origins (SSRF screening). Publishing reuses the M2 engine and approval/hash gates, refuses inactive or unverified connections, uses the instance's configured status limit when available, sends a Mastodon `Idempotency-Key`, and returns `uncertain` without retrying when a send cannot be confirmed. Revoked credentials mark the connection disconnected. Discord/Telegram behavior is unchanged. The `/publishing` UI is still Discord/Telegram only; Bluesky/Mastodon are API-only in this milestone. The `platform_connections` schema additions (`instanceUrl`, `oauthStateHash`, `oauthStateExpiresAt`, `pendingOAuthCiphertext`) have **not** been pushed to the connected database.

**Publishing Milestone 3 security audit:** Mastodon instance URLs are resolved and validated against every DNS answer before any socket (IPv4, IPv6 and IPv4-mapped IPv6; private, loopback, link-local, multicast, reserved and cloud-metadata rejected), the validated address is pinned for the real connection so a rebinding answer cannot be used, redirects are refused rather than followed, and requests carry timeouts plus a response-size cap. OAuth state is 32 random bytes, stored only as a sha256 hash, bound to the initiating user **and** session, expires in 10 minutes, and is consumed by an atomic claim so a callback cannot be replayed or exchanged twice; failed and denied callbacks clear pending data, and the callback redirect is built from the configured app origin, never request host headers. Bluesky refreshes are single-flight per connection with a short reuse window and compare-and-set persistence, so a concurrent refresh cannot overwrite a newer session, refreshed tokens survive a failed or ambiguous send, and switching accounts still invalidates approvals. File-backed connection reads return copies so they behave like Prisma for these checks. The audit added 48 tests: `mastodon_ssrf.test.ts` (20), `prisma_storage.test.ts` (16), Bluesky refresh/token tests (4) and OAuth concurrency/binding tests (8), for a total of 370.

**Publishing Milestone 3 release-readiness audit:** the pinned HTTPS transport now satisfies Node 20+ family autodetection (the custom lookup returns an address array when Node asks for all answers), which the earlier build did not, so live Mastodon requests failed before a socket opened. TLS verification stays on and is bound to the original instance hostname (SNI and certificate name), with only the TCP destination taken from the validated DNS answer; the pinned lookup, TLS options and a real loopback socket are covered by tests. The Bluesky refresh cache key now includes a fingerprint of the refresh token, so a rotated token or a switched account can never reuse a cached session from the old one. Prisma parity tests now cover the publication claim, unique-violation fallback and conditional retry. Final count: 380 tests.

**Publishing Milestone 4 (X):** hybrid free and paid publishing. Manual mode is free: owners compose a weighted thread (Latin 1, CJK/emoji 2, every URL 23, 280 per post, at most 25 posts), copy it, open the X composer, and record `mode: 'manual'` with no connection, no external ids, no API call, and an explicit unverified label in the UI and database. Automatic mode uses X OAuth 2.0 Authorization Code + PKCE with a Crewlink-owned app and the minimum scopes (`tweet.read tweet.write users.read offline.access`); it reuses the M1 vault, the hashed/session-bound/single-use 10-minute OAuth state with atomic claim, and the M2 approval/hash and duplicate gates. Tokens are encryption-at-rest only, refreshed with compare-and-set persistence, and never returned by an API. Threads post sequentially as replies; a 401 refreshes once; rate limits, timeouts and ambiguous responses are recorded as `rate_limited` or `uncertain` and never retried automatically; once any part has an external id the publication becomes a non-retryable `partial_thread`. Pricing lives in one verified module ($0.015 per create request, $0.200 when the request contains a URL, verified 2026-11-11). Automatic publishing shows an estimate, requires explicit `confirmCost` plus an optional `maxCostUsd`, and writes a reservation to the `x_usage_ledger` before sending; reserved and committed rows count against the app-wide `X_MONTHLY_BUDGET_USD` (default 10, invalid values fail closed to 0), and an exhausted budget blocks automatic publishing only. The `/publishing` UI adds both X modes and still covers Discord/Telegram; Bluesky/Mastodon remain API-only. The M4 migration (`prisma/migrations/20261111000000_m4_x_publishing`) has **not** been applied, and the M1–M3 baseline migration is still missing.

**Publishing Milestone 5 (Reddit):** creator-owned Reddit OAuth connections (`identity read submit`, permanent duration, Basic-auth exchange) with the M1 encrypted vault and the same hashed/session-bound/single-use 10-minute state and atomic claim as M3/M4. Subreddit discovery uses only the official API (search, about, rules, post requirements); caches are scoped to user **and** project, and cached permissions are never authoritative because the live requirements are read again immediately before publishing. Drafts carry a required title, a body, a subreddit, and a `self`/`link` type; approval hashes the subreddit, type, title, body, and URL, and an approved link post may have an empty body. Static checks run on save/approve; live checks block private/archived/banned/muted or type-mismatched communities and report anything the API cannot verify (including flair/gallery and moderator judgment) instead of guessing. Publishing reuses the M2 engine, stores the submission id and URL, sends `resubmit=false`, maps HTTP-200 `json.errors` to typed failures, respects `x-ratelimit-reset`, and treats a missing id, timeout, or transport failure as non-retryable `uncertain`. Over-limit titles and bodies are rejected, not silently truncated. The `/publishing` UI adds the Reddit account section, subreddit search/details, text/link composer with safe Markdown and Reddit-style preview, live validation, and history with subreddit/external link. **Publishing Milestone 6 (LinkedIn):** creator-owned LinkedIn member publishing. OAuth 2.0 Authorization Code with `openid profile w_member_social`, a hashed/session-bound/single-use 10-minute state and atomic claim, and no PKCE because LinkedIn does not document it. The callback verifies `GET /v2/userinfo` and stores only encrypted tokens plus the member id; tokens never appear in an API, log, or publication row, and switching accounts invalidates approved drafts. LinkedIn issues no refresh token to ordinary apps, so an expired token disconnects and asks for a reconnect instead of faking a refresh; refresh is used only when LinkedIn actually issued one. Publishing is member-only: organization pages need separate LinkedIn products, `w_organization_social`, and page-admin approval, which are documented but not implemented. Every request reads its version and protocol headers from `src/posting/linkedin/config.ts`; `LINKEDIN_API_VERSION` (default `202610`) must be `YYYYMM` and within LinkedIn's 12-month support window (for example `202511` sunsets on 2026-11-16), and a malformed or sunset value fails closed before a publication is claimed. A post is `POST /rest/posts` with the author URN derived from the verified connection, a 3,000-character drafting guard (the server's `FIELD_LENGTH_TOO_LONG` stays authoritative), and the `x-restli-id` stored as the external id with a feed URL built only from a documented share/ugcPost URN. LinkedIn has no idempotency key, so an ambiguous send stays `sending` and is never retried automatically. No Prisma schema change was needed. The `/publishing` UI adds the LinkedIn account section and composer. Live LinkedIn calls are untested.

**Publishing Milestone 7 (Slack + WhatsApp):** Slack automatic publishing uses the official OAuth v2 install with only the bot scopes `chat:write channels:read groups:read` (no user scopes), the same hashed/session-bound/single-use 10-minute state and atomic claim as M3–M6, and the M1 vault for the bot token. The callback exchanges the code server-side and verifies the bot; only the encrypted bot token, workspace id/name, bot user id, granted scopes, and install metadata are stored. Channel discovery uses the bot token alone, so private channels appear only when the bot is already a member; Crewlink never auto-joins, and a channel is activated only after verifying it is not archived and the bot can post. Changing the channel or workspace invalidates approved drafts, reconnect reuses one connection, and disconnect calls `auth.revoke` and wipes local credentials. Publishing reuses the M2 approval/hash and duplicate gates and additionally requires a verified channel resolved from the connection. `chat.postMessage` sends Slack mrkdwn text (4,000-character limit, link previews), every response is validated by its JSON `ok` flag as well as the HTTP status, and `ts` is stored as the external id. `invalid_auth`/`token_revoked` disconnect; `missing_scope`, `not_in_channel`, `channel_not_found`, `is_archived`, `restricted_action`, `msg_too_long`, and Slack restrictions map to typed failures without dropping a working install. A 429 uses `Retry-After`; an ambiguous send stays `sending`/`uncertain` and is never resent. WhatsApp is manual-only: no Business API, Meta credentials, OAuth, credits, unofficial API, browser automation, or WhatsApp Web session. The owner prepares an approved draft into an official `https://wa.me/?text=…` link, opens WhatsApp, and marks it shared; the manual record goes `prepared → opened → published` through conditional transitions and always reports `verified: false`, so history distinguishes Prepared, Opened in WhatsApp, and Manually marked shared and never says sent or delivered. No Prisma schema or migration change was needed because the existing status and external-id fields are strings. The `/publishing` UI adds the Slack workspace/channel/composer section and the WhatsApp composer/preview/copy/share/manual-confirmation section. Live Slack calls and the WhatsApp share link are untested.

**Publishing Milestone 8 (AI social media agent):** owner-only `/ai` studio that turns one objective into research, a strategy, platform drafts, a review pass, a suggested calendar, and internal analytics. The AI layer lives in `src/ai/` and is provider-independent: `AI_PROVIDER` selects `unconfigured` (production default, features fail closed with `not_configured`), `mock` (deterministic, no network; the default in tests), `openai`, `anthropic` or `gemini`; each real provider uses its own key, base URL, model and HTTP client, and there is no silent fallback between providers. Every response is parsed as JSON and schema-validated, calls are bounded by per-call timeout, retry count, max output tokens and a per-campaign call budget, and keys stay server-side. Research uses only documented search APIs (Brave Search API; Reddit's public search with app-only OAuth) configured through `AI_RESEARCH_PROVIDER`; it stores URL, publisher, published/retrieved timestamps and a summary, marks search results verified and owner-supplied links unverified, moves model-cited URLs it did not retrieve into assumptions, and strips forged `<untrusted>` tags so retrieved text cannot inject instructions. It never invents statistics, quotes or references, and owner-sourced findings stay labelled as assumptions. The strategy covers campaign name, objective, audience, platforms, duration, IANA timezone, themes, posting frequency, calendar, ideas and outcomes; the owner can edit it, and edits reject platforms or durations that break existing ideas. Generation reuses the existing validators for LinkedIn, X threads, Reddit self/link posts, Bluesky, Telegram and Slack, rejects over-limit content instead of truncating it, drops duplicate variations, and saves the rest as ordinary drafts (`status: 'drafted'`) carrying `campaignId`/`contentIdeaId`. One editable brand profile per project (name, description, audience, tone, vocabulary, style, avoid topics/words, CTAs, examples) is included in prompts; nothing is learned from private messages or accounts. Quality returns an advisory score, problems, improvements and only the sources that were actually retrieved, always reports `verificationStatus: 'unverified'`, never claims links were checked, and refuses non-AI drafts. Scheduling is a deterministic heuristic with per-platform minimum gaps, IANA timezone and DST handling, no simultaneous posts and preserved manual overrides; it claims no optimal times and starts no background process. Analytics read only Crewlink's own drafts, publications and schedules; external impressions, reach and engagement are reported as unavailable, and no recommendation is made without enough data. The orchestrator records `ai_agent_executions` and per-stage campaign tasks with explicit states, isolates a failed stage, sanitizes logged errors, and ends the campaign `ready` or `failed`. The AI never receives decrypted platform credentials, never bypasses ownership, never calls a platform API, never approves or publishes, and never changes the existing approval hash, duplicate gates or publish engine. The new Prisma models and the two optional `drafts` columns come from `prisma/migrations/20261113000000_m8_ai_workspace`, which is guarded additive DDL and has **not** been applied; file-backed and Prisma storage paths are covered by parity tests. Live OpenAI/Anthropic/Gemini calls and live Brave/Reddit search are **untested**, and provider pricing is **unverified**, so no cost figure is recorded or shown. Live AI output quality is unreviewed.

## Known traps

- **Repository access stays with the owner.** Approving an applicant changes only their Crewlink status. Never call the GitHub collaborators API during approval or grant write, maintain or admin access. Contributors fork the repository and open pull requests; the owner reviews and merges. The dashboard banner explains this — keep it.
- **Screening is on the honour system.** Crewlink cannot check that someone finished a test. Never word the UI as if completion is verified.
- **AI output is drafts, never approvals.** The AI workspace may create drafts, but approval, hashing, duplicate protection and publishing stay with the existing engine. Never let an agent approve, publish or bypass ownership, and never give it decrypted credentials.
- **Do not invent research or metrics.** Only URLs actually retrieved by the configured search provider count as sources; model-cited links become assumptions. External impressions, reach and engagement are unavailable without official analytics, and provider pricing is unverified, so show no cost claim.
- **Analytics is measured, never estimated.** Only official API values are stored. Missing metrics are null with an explicit unavailable list, never zero; engagement rates require a documented impressions denominator; AI insights are advisory and must state sample size and limitations. Never scrape a dashboard, use an unofficial API, or present a Crewlink calculation as platform-reported.
